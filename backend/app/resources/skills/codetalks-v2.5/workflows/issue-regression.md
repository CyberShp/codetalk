# 问题单/代码修改回归

## 目标

结合问题单、MR、代码 Diff、修改文件和运行证据，重建原故障机制，解释修复如何生效，
并形成完整、可追溯的回归测试方案。

## 一、强制输入和工具

### MR 链接

MR 链接是必需输入。用户已提供时不得重复询问；未提供时必须先询问。

### CodeHub MCP

必须读取 `references/codehub-mr-access.md`，并调用：

```text
codehub-mcp-server
```

读取：

- MR 标题、状态和描述；
- 源分支和目标分支；
- Commit 列表；
- 修改文件；
- 完整或明确范围的 Diff；
- 评审意见；
- 关联问题；
- 可访问的流水线和检查结果。

工具不可用时按固定模板提示安装，Verdict 为 `BLOCKED`，不得继续声称已完成 MR 变更分析。

## 二、材料消费记录

MR 读取成功后，在 `活文档/02-输入材料消费记录.md` 中说明：

- MR 链接；
- 使用的 MCP 工具；
- MR 元数据；
- 修改文件和 Commit 数量；
- 实际读取的 Diff 范围；
- 评审和流水线信息；
- 未读取内容和限制；
- 这些材料支持哪些分析结论。

只记录 MR 链接存在，不算材料消费完成。

## 三、执行流程

1. 区分问题事实、设计预期、问题单判断、源码事实和运行时事实；
2. 重建修复前故障路径：触发条件 → 第一处异常 → 传播 → 最终症状；
3. 逐修改点解释修改前后行为及其阻断的故障路径；
4. 检查是否只是屏蔽症状；
5. 分析调用者、被调用者、状态、资源、锁、时序、错误码、配置和平台影响；
6. 搜索同类实现和相同缺陷模式；
7. 增殖原问题、正常路径、相邻边界、并发、恢复、长稳、N/2N、兼容和二次风险场景；
8. 明确测试方案的新增、修改、删除、保留、合并和待验证项。

## 四、完成门禁

只有以下条件全部满足，才可标记为 READY：

- 用户提供 MR 链接；
- `codehub-mcp-server` 成功调用；
- MR Diff 和修改文件被实际读取；
- 修复前故障路径已重建；
- 修复机制有代码证据；
- 修改影响范围已分析；
- 回归方案覆盖原问题、正常路径、相邻路径和二次风险；
- 未读取内容和限制已记录；
- 独立 Judge 完成适用审查。
