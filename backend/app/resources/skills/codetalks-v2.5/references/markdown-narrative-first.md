# Markdown 叙述优先规则

本文件是深度型 Bootstrap 强制规则。未读取并 ACK 前，不得创建分析工件。

## 一、主事实载体是 Markdown 活文档

本 Skill 的分析内容必须首先写入 Markdown，而不是先写 JSON 后等最终汇总。

Markdown 活文档承担：

- 开发实现讲解；
- 流程、分支、状态和资源解释；
- 异常因果链；
- 风险点；
- SFMEA；
- 测试场景、测试流程和测试用例；
- 覆盖审计。

JSON 只允许用于：

- 运行状态；
- 运行计划；
- 输入材料机器索引；
- 独立审查状态。

JSON 不得作为分析内容的唯一版本，也不得作为用户主要交付。

## 二、禁止“表格即分析”

表格用于索引、对比和追溯，不能代替自然语言讲解。

每张重要表格前后至少要回答：

- 这张表描述的是什么；
- 为什么这些项重要；
- 项目之间有什么因果关系；
- 测试人员应如何理解和使用；
- 哪些项风险最高；
- 哪些内容仍不确定。

禁止只输出大表而没有叙述。

## 三、Flow Card 必须是完整文章

每个核心流程是独立 Markdown 文件，使用 YAML frontmatter 保存机器字段，正文按执行顺序讲解。

正文必须像熟悉代码的开发带着测试人员过流程：

- 先讲用途和上下文；
- 再讲外部如何进入；
- 按时间顺序讲正常流程；
- 逐个解释分支进入条件；
- 解释状态和资源变化；
- 解释异常怎样传播；
- 最后转换为黑盒测试。

不得以 JSON Object、字段清单或函数列表代替叙述。

## 四、正式输出必须边分析边更新

不能等全部 JSON 写完后，最后才生成 Markdown。

每一步完成时必须同步产生对应 Markdown 活文档和正式输出章节。

后续发现新证据时：

1. 更新事实；
2. 更新受影响 Flow Card；
3. 更新风险、SFMEA 和测试追溯；
4. 更新正式 Markdown。

## 五、终端不得倾倒 JSON

终端只展示：

- 本步骤完成情况；
- 关键分析结论；
- 生成或更新的 Markdown 文件；
- 阻塞和下一步。

不得把 JSON 内容当作报告打印给用户。

## 六、长度阈值只是防空壳门禁

脚本会检查 Markdown 和 Flow Card 的最低内容量、必要标题和叙述段落。

这些阈值仅用于阻止空模板、纯表格和极短输出，不代表达到阈值就分析完整。
最终质量仍由 Coverage Judge 根据证据和语义完整性判断。
