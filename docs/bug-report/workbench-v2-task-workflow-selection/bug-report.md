# 新建任务无法选择内置工作流

## 现象

正式数据包含 79 个内置工作流，但 `/tasks/new` 仅显示一条原生 V2 探针工作流。用户无法选择模块分析等正式预设。

## 根因

1. 旧工作流迁移只保存 `compiled_definition`，`compiled_plan` 为空，不能满足 V2 任务创建契约。
2. 工作流列表接口主动排除了所有内置工作流的 V2 发布信息。
3. 任务向导额外要求 `authoring_graph.schema_version === 2`，误删了可通过兼容计划运行的只读迁移工作流。
4. 原验收只在测试中创建原生 V2 工作流，未覆盖正式库中的存量内置预设。
5. 旧预设的保留输入 `repo_path` 使用 `local` resolver，导致选过工作空间后仍要求用户重复填写源码路径。
6. 修复官方快照后，旧影子版本仍保持历史发布状态；新任务接口若只检查 `published`，可通过旧版本 ID 绕过当前官方指针。

## 修复

- 工作流迁移版本升级为 2，使用既有 `compile_legacy_workflow` 为存量发布版本补齐兼容执行计划。
- 兼容计划回填只处理带 `legacy_definition` 的 schema v1 快照，绝不把缺 plan 的原生 V2 DAG 降级为顺序计划。
- 列表接口为内置预设附加发布版本信息，同时继续以代码内官方定义为准，避免同名影子记录污染。
- 启动与列表读取都会校验内置 ID 的完整发布快照，包括 definition、只读 graph、顺序 plan、validation 和 header 状态；发现同名或篡改 shadow 时保留旧历史并创建新的官方只读发布快照。
- 内置 ID 的 V2 修改、归档、草稿、校验、编译、发布和试运行入口统一返回只读冲突；遗留草稿会被归档并从 header 解除。
- 列表存在草稿时仍投影 published 内容，避免展示 draft 却执行 published。
- 任务向导展示所有带发布版本的工作流，不再以作者图版本判断可运行性。
- V2 任务将 `repo_path` 目录输入视为工作空间保留字段，页面不重复展示，运行时由后端注入所选工作空间路径。
- API 提交的工作空间保留字段会在入库前剔除，任务定义与运行快照不会出现两套路径真相。
- 新建或克隆内置工作流任务只能使用 header 当前指向的官方发布版本；旧版本继续供既有任务读取、重跑和审计，兼顾安全边界与历史可复现性。

## 回归门禁

- 新迁移和存量回填都必须生成 `legacy_sequential` 执行计划，且重复迁移不得再次修改。
- `module_analysis` 必须带 V2 发布版本出现在列表中。
- 迁移后的旧工作流必须能真实创建并编译 V2 任务。
- 浏览器必须从 `/tasks/new` 选择内置工作流并进入后续步骤。
- 迁移工作流无需用户填写 `repo_path`，任务 Attempt 快照必须包含真实工作空间路径。
- 已被官方快照替换的影子版本不得创建或克隆新任务，但绑定该版本的既有任务仍必须可读取。
