# CodeTalk Workbench V2 用户手册

Workbench V2 用于把代码理解、测试分析和 Agent 执行变成可重复、可审计、可下载的工作流。正常使用不需要编辑 JSON，也不需要手动输入仓库路径或调用后端 API。

## 1. 先理解四个对象

| 对象 | 回答的问题 | 是否可修改 |
|---|---|---|
| Workflow | 以后按什么步骤执行，收什么输入，调用什么能力，交付什么文件 | 草稿可改，发布版本不可改 |
| Task | 这一次要分析哪个工作空间、目标和材料 | 草稿可改，运行后保留定义 |
| Run Attempt | 这一次实际执行时冻结了哪些输入、配置和计划 | 不可原地修改 |
| Asset | 哪些语义用例和源码证据可供以后复用 | 可编辑、废弃、恢复和追踪 |

固定继承顺序是：

```text
系统默认 -> 已发布 Workflow Version -> Task 本次覆盖 -> Run Attempt 冻结快照
```

Task 重试会创建新的 Attempt，不会覆盖上一次运行，也不会偷偷读取后来修改的工作流或 Task 配置。

## 2. 第一次完整运行

### 2.1 准备工作空间

1. 打开 `/workspaces`。
2. 新建工作空间，填写可读名称并选择真实本地 Git 仓库。
3. 等待工作空间创建完成；可选索引失败不阻止本地源码读取，但页面会显示降级状态。
4. 在工作空间详情确认目标源码或材料可访问。

工作流和 Task 只选择已创建工作空间。用户不需要再次输入仓库路径。

### 2.2 准备已发布工作流

1. 打开 `/workflows`。
2. 选择已有已发布工作流，或点击“新建工作流”。
3. 六步向导依次完成基本信息、输入、执行节点、输出、流程和验证发布。
4. 点击“验证”，修复所有阻断问题。
5. 点击“编译计划”，确认真实执行顺序与画布一致。
6. 需要时选择工作空间进行试运行；试运行不会自动发布。
7. 点击“发布工作流”。

发布后需要修改时，从该版本创建新草稿；旧 Task 仍引用旧版本。

### 2.3 创建 Task

1. 打开 `/tasks`，点击“新建任务”。
2. 选择已发布工作流。
3. 填写 Task 名称并选择工作空间。
4. 按工作流定义填写本次输入。
5. 普通运行保持“继承工作流默认”；只有本次确有差异时才覆盖 Agent、Skills、MCP 或输出。
6. 检查汇总后选择“保存草稿”“保存为就绪任务”或“保存并运行”。

文件会由浏览器真实上传并复制到运行输入快照。MR 链接、目标文本和测试约束按原文传给执行器，不应只截取第一行。

### 2.4 在驾驶舱验收

运行后进入 `/tasks/{taskId}/runs/{runId}`。建议按以下顺序看：

1. 顶部执行、质量、交付状态。
2. 当前节点与节点列表。
3. “公开输出”中的 Agent 结论和进度。
4. 交付件列表、预览和下载。
5. 失败时的中文原因、可重试性和建议操作。
6. 仅在排障时展开技术诊断、原始事件和支持文件。

## 3. 如何设计工作流

### 3.1 输入节点

每个输入都要有唯一 ID、面向用户的名称、类型、必填性和填写说明。名称会直接成为 Task 向导的提示。

| 类型 | 适合内容 | Task 中的表现 |
|---|---|---|
| `directory` + workspace | 源码仓库 | 工作空间选择器自动解析 |
| `text` / `long_text` | 模块、目标、测试约束 | 单行或多行输入 |
| `file` / `file_set` | 需求、设计、缺陷、覆盖率 | 单文件或多文件上传 |
| `mr_link` | Merge Request / Pull Request | 链接输入 |
| `patch` | Diff 或补丁 | 文本或文件材料 |
| `coverage_report` | lcov、gcov 等覆盖率产物 | 文件上传 |

不要把“需求文档、设计文档、MR 链接”合并成一个含糊的 `inputs` 字段。分别命名后，Task 用户才知道应该提供什么，Agent 也能知道每份材料的角色。

### 3.2 Agent 节点

Agent 节点至少定义：

- 一个明确、可验收的节点目标。
- Provider：内置模型或设置页发现到的外部 Agent。
- Skills：例如源码证据优先、SFMEA、黑盒测试设计、产物契约。
- MCP Profiles：只显示该 Provider 声明可用的配置，并支持搜索。
- 输入和输出端口、超时、空闲超时、重试及失败策略。
- 必须写出的 artifact 文件。

Provider 切换后，MCP 选项会按该 Provider 的能力重新计算。工作流发布时这些默认值被冻结，Task 只保存明确的本次覆盖。

### 3.3 处理和校验节点

工作流还可使用语义检索、证据检索、本地范围发现、证据校验、报告渲染和产物导出节点。这些节点不是视觉装饰：编译器会把画布连线转为有向无环执行计划，Scheduler 只在所有依赖成功后运行下游节点。

孤立节点、环、端口类型不兼容、不可用 Provider、未知 Skill/MCP、不安全 artifact 路径和缺失 JSON Schema 会在发布前阻断或给出明确警告。

### 3.4 输出节点

输出既提醒用户会得到什么，也约束执行器必须生成什么。每个输出应配置：

- 可读名称和唯一输出 ID。
- `markdown`、`json` 或 `test_cases` 类型。
- 安全且唯一的相对文件名。
- 来源节点和来源端口。
- 是否必需、是否进入语义库或证据库。
- JSON 输出的结构 Schema。

大段 SFMEA、测试设计和黑盒用例应写入文件，不应把整个终端输出当最终交付。

### 3.5 画布操作

- 从左侧节点库拖入或双击添加节点。
- 鼠标左键拖动节点，拖动画布空白区域进行平移。
- 从输出端口拖到目标输入端口建立连线。
- 点击节点后在属性区编辑；点击空白区域关闭属性区。
- 选中节点或连线后按 Delete/Backspace 删除。
- 使用工具栏或 `Cmd/Ctrl+Z` 撤销。

画布是唯一事实源。表单操作直接修改同一张图；JSON 不是第二套可写配置。

## 4. 测试活动怎么落地

### 4.1 代码分析到黑盒用例

推荐 DAG：

```text
工作空间 + 需求/MR/约束
  -> 本地范围发现 / GitNexus / CGC
  -> 源码证据与关键流程
  -> SFMEA
  -> 黑盒测试设计
  -> 证据与结构校验
  -> Markdown/JSON 交付件
```

对于 SPDK iSCSI login，可把目标写为：

```text
基于 lib/iscsi 与 test/iscsi_tgt，梳理 login 到 full feature phase。
覆盖 CHAP、digest、多连接、认证失败、超时、session reset、initiator 断开与恢复。
黑盒步骤只使用外部配置、网络操作、RPC、日志、指标和状态观测。
```

合格输出至少包含真实源码证据、主/异常/恢复流程、可解释的 S/O/D 与 RPN、可执行黑盒用例，以及证据缺口。

### 4.2 专业性从哪里来

专业内容不应只靠模型自由发挥。稳定交付由四层共同限定：

1. Workflow 输出契约定义章节、字段、文件和 Schema。
2. Skills 定义测试方法和质量边界。
3. 项目/领域画像定义协议、模块、风险分类和常见观测点。
4. 证据校验与质量门禁检查引用、覆盖、黑盒边界和 artifact 完整性。

用户只给“NVMe TCP TLS”时，工作流应先发现源码和测试资产，再依据协议与项目画像生成适用风险；无法由证据确认的内容必须标记为假设或缺口。

## 5. 状态和失败恢复

### 5.1 三类运行结果

| 状态 | 含义 |
|---|---|
| Execution | 是否排队、运行、成功、失败、取消或中断 |
| Quality | 是否未检查、待检查、通过、警告或阻断 |
| Delivery | 没有交付、部分交付或全部交付 |

“执行成功”不等于“质量通过”，“声明了输出文件”也不等于“文件已交付”。驾驶舱会分别显示三类结果。

### 5.2 判断是否真的运行

正常运行至少应出现：

- Run Attempt 编号和开始时间。
- 节点从等待进入运行再进入终态。
- 增量公开事件或 Agent 输出。
- 与输出契约一致的真实文件。
- 质量和交付状态的最终结论。

任务在不到一秒内完成但没有节点事件、实际输出或 artifact 内容，不能视为成功，应查看失败摘要和技术诊断。

### 5.3 重试与中断

- 可恢复失败使用“从失败节点重试”。系统创建新 Attempt，复用成功上游结果并执行受影响下游。
- 不可恢复配置错误先回到工作流或复制 Task 修改配置。
- 服务重启会把遗留 queued/running Attempt 标记为 interrupted，不会伪装成成功。
- 历史 Attempt 和 artifact 始终保留可读。

## 6. 语义库和证据库

### 6.1 测试语义库

支持 FTS5 关键词搜索、字段筛选、详情编辑、复制、废弃、恢复和来源/运行引用。导入流程固定为上传、字段映射、预览验证、冲突策略、确认提交。

冲突策略只有：`skip`、`overwrite`、`create_new`。缺 Case ID、场景或预期结果的行不会被静默补齐，失败记录可下载。

### 6.2 证据库

证据库读取现有 Evidence Memory，展示来源、置信度、工作空间、运行引用和真实 source slice。源文件删除或不可用时应显示降级信息，不会制造一个看似存在的片段。

## 7. 性能和大结果

- Task、语义和证据列表默认每页 25 条，最大 100 条。
- 搜索在停止输入 300ms 后请求，避免每个键触发后端查询。
- 驾驶舱首次加载最新事件，前端最多保留 2,000 条；点击“加载更早事件”分页回看。
- 实时输出通过 SSE 增量追加，不重复下载完整日志。
- 工作流画布目标规模为 200 节点；超大图第一阶段不承诺虚拟化。

## 8. 兼容与回滚

Workbench V2 默认启用。设置后端环境变量并重启可恢复旧入口：

```env
WORKBENCH_V2_ENABLED=false
```

回滚开关只改变入口，不删除 V2 或旧数据。重新设为 `true` 后恢复 V2。详细备份、部署和故障恢复见 [`DEPLOYMENT.md`](DEPLOYMENT.md)。

## 9. 验收清单

- 工作流不用编辑 JSON 即可验证、编译、试运行和发布。
- 编译计划与画布连线一致，发布版本不可修改。
- Task 只显示所选工作流命名的输入，工作空间从已有列表选择。
- 默认 Agent/Skills/MCP/输出可直接继承，本次覆盖不修改发布版本。
- Run Attempt 显示真实节点、事件、三类状态、失败原因和交付文件。
- 重试创建新 Attempt，旧运行和产物仍可访问。
- 语义导入先预览再提交，证据来源可打开。
- 页面在 1440、1280、1024 宽度无横向溢出和双主滚动。
- 键盘可完成向导，并能选择和删除画布节点。
- 完整密钥、敏感环境变量和私有运行路径不出现在公开 UI 或报告中。
